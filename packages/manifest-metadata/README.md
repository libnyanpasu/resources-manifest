# @manifest/metadata

Resource manifest TypeScript definitions, version constants, and JSON Schema,
generated by `crates/manifest-schema-generator` from the Rust metadata in
`crates/manifest-metadata`. Parser/checksum types belong to `crates/manifest-parser`
and reach the generator through metadata's type graph.

Never hand-edit `src/types.ts`, `src/version.ts`, or `schema/`. Regenerate from the
repository root:

```sh
pnpm run generate:schema
```

## Exports

- `@manifest/metadata`: all `types.ts` types and `RESOURCE_MANIFEST_VERSION`.
- `@manifest/metadata/types`: generated type definitions only.
- `@manifest/metadata/schema/manifest`: JSON Schema for compiled `ResourceManifest`.
- `@manifest/metadata/schema/template`: JSON Schema for compiler input
  `ResourceManifestTemplate`.
- `@manifest/metadata/schema/snapshot`: JSON Schema for the generator's release
  snapshot `ManifestSnapshot`, the compiler's second input.

## Contract layers

TypeScript and JSON Schema are structural contracts aligned with the wire format:

- `manifest_version` is a `"<major>.<minor>"` string with major fixed to 2. The TS
  type is `` `2.${number}` ``; the schema pattern is `^2\.(0|[1-9][0-9]*)$`, rejecting
  leading zeros. The TS template literal is wider than the wire format and permits
  values such as `"2.1.5"`; validate with the schema pattern and Rust parser rather
  than TS alone. Rust also requires the minor to fit `u32`. The generated version
  constant is `"2.0"`; both schema `$id` values include `/schema/2.0/`.
- `ResourceChecksum` permits only `<algorithm>:<hex>` through its TS template
  literal/schema pattern, and schemas require normalized lowercase. Templates carry
  no checksums: static history and remote fallbacks come from the snapshot.
- Snapshot IDs are decimal strings (`^[0-9]+$`), because a JS number cannot hold
  every GitHub ID. Templates and snapshots reject unknown fields.
- Optional TS/schema fields accept absence or a concrete value, never null.

Semantic and cross-field rules are outside this package: tag-combination
uniqueness, correct `tag_key`, mutually exclusive tag groups, platform defaults,
registry/mirror references, `latest` appearing in `releases`, and resolvable template
variables. See [Validation invariants](../../docs/design/manifest-v2.md#validation-invariants).
These belong to compiler/validator code, with current compiled-manifest validation
in `manifest-core` through runtime; the `@manifest/generator` compiler work remains
a separate milestone. JSON Schema does not declare these semantics.

## Deliberately permissive decoding

Rust optional fields deserialize explicit null as `None` (Serde `Option` behavior),
which is wider than the TS/schema contract. Serialization never emits those null
fields. Consumers requiring strict null rejection should validate against JSON
Schema, as illustrated by downloader's Ajv tests, rather than Rust types alone.

Rust accepts any valid minor under the same major.
`ManifestVersion::is_newer_minor()` identifies versions above `CURRENT_MINOR`.
Version errors expose stable `code()` and the `manifest_version` path: malformed
format gives `manifest.invalid_version_format`, another major gives
`manifest.unsupported_major` with the structured `major` field. Generated TS and
schemas describe the current minor's structural contract. Consumers must not reject
a newer minor solely because an old schema fails; consumer semantic validation
uses `validate_manifest`.

Compiled Rust decoding skips unknown platform keys in `artifacts` and
`default_variants`; unknown version/checksum parser tags become Rust-only
`Unsupported { parser_type }` variants preserving the original tag. These variants
are deliberately absent from generated TS and schemas. Template decoding rejects
unknown platforms and parser tags. See the full
[Versioning contract](../../docs/design/manifest-v2.md#versioning).
